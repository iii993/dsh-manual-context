# 项目说明：手动上下文编辑器（`@dsh-external/manual-context`）

> **读者**：第一次接手这个插件的人。看完这一份 + `docs/接口契约.md` 就能改代码。
> 历史事故的完整复盘在 `docs/会话格式与手动上下文-经验总结.md`。
> 面向用户的功能说明在 `README.md`。
>
> **本次审查快照**：`node --test tests/*.test.mjs` = 115 项全过（约 1.4 秒）。
> 第 6 节「已知陷阱」里有 4 条是**本次审查新发现、尚未修复**的，已标注 ⚠️。

---

## 1. 这个插件做什么

1. **手动上下文自动注入**：扫描 `<工作区>/manual-context` 与 `$DSH_HOME/manual-context` 下的
   `.md` / `.txt` 条目，把它们变成会话 surface 上的**真实消息节点**（可编辑、可删除、可重排）。
2. **对话历史编辑**：在 Web 面板里编辑 / 删除 / 拖动重排模型可见历史。
3. **上下文导入导出**：把对话导出成 JSON，再导入成历史消息或手动上下文条目。

它不做的事：不注册自定义事件类型（外部事件过不了持久化校验）、不改系统提示词
（每轮由 Harness 重渲染）。

## 3. 数据流

### 3.1 条目 → 排队 → 写入

```text
① 条目文件（*.md，frontmatter + <!-- role: xxx --> 段标记）
        │  store.parseSegments / parseEntry
        ▼
② entrySegments(entry)            inject.js:49-71
   → 每段 {id, index, role, text, tool, args, callId, isError}
   id = "manual-context:r3:<条目hash>[:<段号>]"   ← 去重与幂等的唯一依据
        │
        ▼
③ planTargets(cwd, warnings)      inject.js:79-161
   · 跳过 enabled:false
   · 连续的 reasoning/assistant/tool-call 段**合并成一条** assistant 消息（多内容块）
   · user 段 / tool-result 段是分界线，各自独立成消息
   · tool-result 段向前配对最近的未配对 tool-call（配不上 → 跳过并记 warning）
   · 排序：weight<=0 排系统提示词下方，weight>0 排对话末尾（权重降序）
        │
        ▼
④ syncManualContext(ctx, sessionId)   inject.js:283-361
   · 总开关关：把已有 manual-context 节点整体遮蔽 → 返回 {disabled:true}
   · 差集：present（surface 上已有的 id） vs wanted → added / removed
   · 逐条容错：写不进去的记 deferred，能写的先写
   · 顺序不对才 reorderIfNeeded（遮蔽+重放；发现会移动 system 节点就放弃）
        │  写不进去（code = session-write-pending）
        ▼
⑤ 队列 $DSH_HOME/manual-context-edits/<sid>.queue.json   http.js:319-323 / 432-435
        │
        ▼
⑥ agent/request（step/start 之后、请求组装之前）
   applyQueuedOperations()   index.js:27-34 → http.js:512-549
   · 无开放 turn/step → 跳过并记 apply.log
   · 逐条 runOperation 重放；失败留队列（>5 次放弃）；结果写 apply.log
```

**三个时机点**（改代码时最容易搞混）：

| 时机 | 位置 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| `agent/pre-step`（每 turn 首步） | `inject.js:421-438` | **只能排队** | 写日志（`step/start` 还没发生） |
| `agent/request`（step 已开、请求组装前） | `index.js:27-34` | 应用队列（写 `append` 事件） | 假设系统提示词已经在 surface 上（⚠️ 陷阱 6.1） |
| 面板 HTTP 请求（可能空闲） | `http.js:207-438` | 写文件、改队列；能写就写 | 空闲时写 surface（抛 pending → 排队） |

### 3.2 历史编辑链路

```text
面板 save-edit / delete-part / delete-messages / reorder-messages
   → history.applyEdit / deletePart / deleteMessages / reorderMessages
      · 形状自检      assertWritableEvent      history.js:381-431
      · 生命周期守卫  writablePosition         history.js:820-827
      · 现场构建全部事件 → 再动日志（构建失败整体放弃，不留半截）
```

两条写入策略：

| 目标 | 策略 | 原因 |
| --- | --- | --- |
| `user/message` / `tool/result` / 非头部 `system/message` | **原位替换** `surfaceOp:{op:'replace',startSeq,endSeq}` + `sourceEventSeqs` | 位置不变 |
| `assistant/message` | **遮蔽原节点 + 尾部按原顺序重放** | assistant 不能带 `sourceEventSeqs`，做不了替换；单次上限 `REPLAY_LIMIT=2000` |
| 删除 / 重排 | 空内容 `system/message` 遮蔽（不投影消息） | 节点位置保持不变 |

### 3.3 编辑档案与队列（都在 `$DSH_HOME/manual-context-edits/`）

| 文件 | 内容 |
| --- | --- |
| `<encodeURIComponent(sessionId)>.json` | 编辑档案 `{sessionId, edits:[{seq,replacedSeq,targetType,targetText,protected,updatedAt}], updatedAt}` |
| `<…>.queue.json` | 排队操作 `{sessionId, operations:[{op,payload,requestedAt,attempts?}], updatedAt}` |
| `apply.log` | 每次排队应用的流水（完成 / 重试 / 放弃 / 跳过 + 原因） |

## 4. 会话格式约束速查

写入前必背。仓库内的等价模型：`src/repair.js:205-276`（`foldSurface`）、
`src/history.js:373-431`（`ROLE_BY_TYPE` + `assertWritableEvent`）。

### 4.1 surface 折叠的三条硬规则

| # | 规则 | 违反后的报错 |
| --- | --- | --- |
| 1 | surface **第一个节点必须是 `system/message`**（`protectedHead`）；surface 非空且 head 未定时再写 `system/message` 直接拒 | `system/message requires a protected first surface head` |
| 2 | 除 `user/message` 外，表面事件必须落在**打开的 turn+step** 里；**替换形式**的 `tool/result` 只要求打开的 turn | `assistant/message does not match an open turn and step` / `tool/result …` |
| 3 | 遮蔽事件（带 `sourceEventSeqs`）的 source 必须是 `system-prompt`（只有 `system/message` 能带这个标记） | `message must have system-prompt source` |

补充：替换 head 节点时，替换事件必须**恰好一个 `system/message`**，否则
`protectedHead` 保护失败（`src/repair.js:265-270`）。

### 4.2 事件形状（`assertMessageEventShape` 等价表）

| 事件 | role | source | 其它 |
| --- | --- | --- | --- |
| `user/message` | `user` | kind 非空 | `data` 就是 message 本体 |
| `assistant/message` | `assistant` | `model` + `provider` / `model` | 需 `turn/step/stream`；**不能带 `sourceEventSeqs`** |
| `tool/result` (v3) | `user` | `tool` + `callId` | content 恰好 1 个 `tool-result` 块，块内 `toolCallId` 与 `source.callId` 一致 |
| `tool/result` (v4) | `tool` | `tool` + `callId` | message.`toolCallId` 与 `source.callId` 一致；content 里不能再有 `tool-result` 块 |
| `system/message` | `system` | 遮蔽 = `system-prompt`，普通 = `plugin:…` | 不能是裸 `kind:'plugin'`（v4 拒绝） |

### 4.3 v3 / v4 差异

| 项 | v0–v3 | v4 |
| --- | --- | --- |
| `tool/result` | `role:'user'` + 一个 `tool-result` 包装块 | `role:'tool'` 一等消息，`toolCallId` 在 message 上 |
| 工具轨迹重放（`assertReplayable`，`src/history.js:509-526`） | **拒绝**（缺配套 `tool/call`） | 允许 |

> ⚠️ 会话版本有两个数据源：`src/history.js:787-790` 用 `session.header.version`，
> `src/http.js:149` 用 `session.sessionVersion ?? session.header?.version`。
> 两者不一致时会按错误形状写 `tool/result`（陷阱 6.4）。

### 4.4 其它不可违反的点

- **`tool/result` 的 surface 替换只允许改 `content`**：`replaceInPlace` 直接拿原 message 做底，
  保住 `id` / `role` / `source` / `toolCallId` / `isError`（`src/history.js:567-573`）。
- **系统提示词（surface[0]）不可替换、不可删除、不可重排**：每轮由 Harness 重渲染。
- **日志是分帧 zstd，第一帧必须恰好只装 header 一行**（离线重写时才会踩到，`tools/repair-*.mjs`）。

| 测试文件 | 覆盖 |
| --- | --- |

| `tests/host.test.mjs` | 注入同步与幂等、权重排序、合并组、空闲排队、`applyQueuedOperations`、形状自检、编辑 / 删除 / 片段 / 重排、导入导出往返 |
| `tests/client.test.mjs` | 面板渲染（用 `useState` 调用序号覆盖初值的渲染测试）、导入按钮与结果文案 |
| `tests/repair.test.mjs` | 三类坏法的修复计划；拿不到 dsh 校验器时相关用例自动 skip |

**测试替身的盲区（本次审查确认，改代码时必须知道）**：
`tests/host.test.mjs` 的假会话（`contextSession` 39-78、`movableSession` 923-960）
只维护 `surface.nodes` 的 append / replace 语义，**完全没有实现 `protectedHead` 折叠规则**，
也不建模「turn/step 开着但 surface 还是空的」这个 request 时机。
例如 `tests/host.test.mjs:601-632` 直接把一个 `tool/result` 当 surface 首节点来编辑 ——
真实 dsh 会拒这份日志，测试却通过。
所以：**任何关于 surface 首节点 / 写入时机的改动，都不能只靠现有测试判断**，
参照 `src/repair.js:205-276` 的 `foldSurface` 写断言，或用 `verifySession` 走真实加载校验。

## 6. 已知陷阱清单

### 6.1 ⚠️（未修复）「turn/step 开着」不等于「可以写 surface」

- 守卫只看 turn/step：`src/history.js:799-827`；排队应用前的门槛同理 `src/http.js:520-524`。
- 但 surface 首节点必须是 `system/message`（规则 1）。`agent/request` 发生在系统提示词写进
  surface **之前**，此刻新会话的 surface 是空的 → 排队的导入 / 注入会把 `user/message` 写成首节点 →
  系统提示词随后写入 → 会话再也打不开（`session-b526d0d4` 事故）。
- 同一仓库里 `src/inject.js:230-245`（假设系统提示词不是 surface 节点）与
  `src/repair.js:242-247`（假设首节点必须是 system/message）**假设相反**。
- 修的方向（供参考）：写入前确认 surface 已有 head（`session.surface.nodes[0]` 的
  `deriveEventMessage` 是 `role:'system'`，或 foldSurface 的 `protectedHead` 已定）；
  未定就继续排队、等下一轮。`status.canWrite` 与前端文案要同步改。

### 6.2 ⚠️（未修复）`replaceInPlace` 没有生命周期守卫

`src/history.js:561-590` 不做任何时机检查，`applyEdit`（732-734）与 `deletePart`（1067-1069）
在非 assistant 目标上直接调用它 → **空闲时编辑会立刻写日志**（`user/message` 甚至不报错），
写出 turn 之外的表面事件。其余写入路径都走 `writablePosition`。测试未覆盖空闲 `save-edit`。

### 6.3 ⚠️（未修复）`blocks` 通道的 `tool-call` 缺 `callId`

`src/history.js:897` 用 `block.callId`；`edit-pending`（`src/http.js:361`）与面板「＋新增」
（`src/client.js:1085`）都不传 → 块的 `id` 为 `undefined` → 工具返回永远配不上对。
导入通道 `importedBlocks`（`src/http.js:640-648`）反而总是补齐。

### 6.4 ⚠️（未修复）会话版本有两个数据源

`src/history.js:787-790` 用 `session.header.version`；`src/http.js:149` 用
`session.sessionVersion ?? session.header?.version`。不一致时面板显示的版本与
实际写入形状（v3 / v4 的 `tool/result`）会对不上。

### 6.5 `session-write-pending` 是**排队信号**，不是失败

- 抛错点：`src/history.js:799-827`；捕获并转成排队：`src/http.js:428-437`。
- 返回 `{ok:true, queued:true, message}`；前端弹「改动已排队」提示条（`src/client.js:199`），
  **不要**在 UI 上标红。
- 队列应用失败也**不丢**：留在队列里重试 ≤5 次（`src/http.js:533-544`），
  排查看 `apply.log`（`src/history.js:49-63`）。

### 6.6 `tool/result` 的文本藏在**嵌套** content 里

真实结构是 `{type:'tool-result', toolCallId, content:[{type:'text',text}]}`；
只扫顶层 `type==='text'` 会得到空串。取文本用 `toolResultText`（`src/freeze.js:24-41`）。

### 6.7 `assistant/message` 不能带 `sourceEventSeqs`

所以模型输出做不了 surface 替换，只能「遮蔽 + 尾部重放」；单次上限 `REPLAY_LIMIT = 2000`
（`src/history.js:629`, `640-681`）。超过就明确拒绝，不写半截。

### 6.8 类型要看**消息**，不能只看事件类型

编辑历史时会用同类型事件承载角色相同的消息，但工具返回的判断要看 content 里有没有
`tool-result` 块（`kindFromMessage`, `src/history.js:183-193`）。

### 6.9 主对话流不会变

`dsh-client-ui-conversation` 只在重建系统提示词时读 surface，主对话流渲染的是原始事件日志。
**编辑是否生效以本面板和模型的回答为准**，不要看主对话流。

### 6.10 前端源码改了必须重启 dsh web

刷新页面只重读浏览器 bundle；宿主进程里的插件模块不会重载。
HTTP 404 / `宿主插件未挂载 /manual-context 路由` 基本都是这个原因（`src/client.js:186-188`）。
路由服务名是 **`webServer`**（写 `ctx.inject(['httpServer',…])` 会静默不执行）。

### 6.11 `pnpm install` 会 prune 掉手工 junction

本插件通过 junction 挂在 `$DSH_HOME/profiles/web/node_modules/@dsh-external/manual-context`；
profile 用 hoisted 模式，install 会清掉不在 lockfile 里的顶层包 → 跑 `node tools/relink.mjs` 重建后重启。

### 6.12 `node tools/repair-migration.mjs` 必须走真实加载校验

`validation:'transformed'` 不跑关系校验 —— **用它验证等于没验证**（`src/repair.js:486-489`）。
会话打不开（`protected first surface head` / `does not match an open turn`）时先修日志再谈代码；
修完要**重启 dsh** 才会重新读盘。

### 6.13 队列下标不可当稳定 id

`queueIndex` 是位置下标（`src/http.js:449-504`）；面板 2.5s 轮询期间队列可能变化，
`drop-pending` 会删掉该下标上的任意操作（`src/http.js:325-336`）。详见 `docs/接口契约.md` 的 B4。

## 7. 新成员接手清单

1. 读本文 + `docs/接口契约.md`；用户视角读 `README.md`。
2. 跑一遍 `node --test tests/*.test.mjs`，确认 115 项全过，建立基线。
3. 记住三条铁律：
   - **只有 `history.js` 写日志**，且写入前必须过 `assertWritableEvent` + `writablePosition`；
   - **写不进去就排队**（`session-write-pending`），永远不要在空闲时硬写；
   - **surface 首节点必须是 `system/message`**（陷阱 6.1），request 时机不保证这点。
4. 改写入相关代码前，先看 `src/repair.js:205-276` 的 `foldSurface`（仓库内的格式规则等价物）
   与 `tests/host.test.mjs` 的假会话，判断自己的改动有没有被测试替身建模。
5. 遇到「会话打不开、界面空白且不报错」，按顺序查：
   `apply.log` → 队列文件 → `node tools/repair-migration.mjs`（先不带 `--apply` 预览）
   → 修复后**重启 dsh**。
6. 改 HTTP 接口 / 返回字段前后，对照 `docs/接口契约.md` 第 6 节（前端依赖字段）与第 7 节（歧义）。
