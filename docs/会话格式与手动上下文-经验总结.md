# 经验总结：DSH v4 会话格式与手动上下文插件演进

> 本文记录 2026-09 那次「升级 dsh 0.1.7-alpha 后部分对话打不开」的完整排查与修复，
> 以及随后给 @dsh-external/manual-context 增加的四项功能（surface 同步注入、保存不跳转、
> 注入开关与权重、对话导出导入）中踩到的所有坑。
>
> 目的：下次遇到会话格式问题、surface 写入问题或改这个插件时，能直接照着做，不用重新摸索。

---

## 一、症状与第一手证据

升级到 dsh **0.1.7-alpha.1** 后，个别对话打开时报：

```
历史加载失败：failed to observe session "session-<会话 id>":
Session migration from v3 to v4 refuses the transformed artifact:
system/message does not match an open turn and step
（gateway/internal）
```

关键线索：

- 出错的全是 **v3 格式**的老会话（`session.v3.jsonl.zstd`）；同目录下的 v4 会话正常。
- 出错的会话**都用过上下文编辑插件**（日志里有 `manual-context-moved:` / `manual-context-move:` id 前缀）。
- 全量扫描 77 个会话文件，只有 4 个失败（都是 v3 格式的老会话，会话编号从略）。

**经验 1**：不要凭报错猜。先把 `$DSH_HOME/sessions` 下所有 `*.jsonl.zstd` 逐个跑一遍真实迁移路径，
得到准确的失败清单——77 个里只有 4 个坏，范围立刻收敛。

## 二、根因：v4 迁移新增的「生命周期」硬约束

v3→v4 迁移器（`@deepseek-ai/dsh-session-format-v3-to-v4`）会强制检查表面事件与 turn/step 的关系：

| 事件 | v4 要求 |
| --- | --- |
| `system/message`、`developer/message`、`assistant/attempt`、`assistant/message`、`tool/call` | 必须匹配**开放**的 turn 与 step（`data.turn`/`data.step` 等于当前 open 值） |
| `tool/result`（`surfaceOp:'append'`） | 匹配开放 step，且**结算一个已声明的工具调用**（该调用还必须是 started 的） |
| `tool/result`（`surfaceOp:{op:'replace'}`） | 只要求存在开放 turn，**不比对坐标、不复核调用生命周期** |
| `user/message` | 无要求 |
| `turn/start` / `step/start` | 编号必须等于 `nextTurn` / `nextStep`（不能跳号、不能重开） |
| `step/end` / `turn/end` | 不能留下未结算的已声明工具调用 |

而 `dsh-session` 的 **`Session.append` 只做事件本地校验**（surfaceOp / sourceEventSeqs / 首节点保护），
其文档原话是 *"history relations are not checked"* —— 所以 **v3 时代怎么写都不会当场报错，
只有下次加载（迁移）时才炸**。

插件当时的问题：面板**空闲时**（上一次 `turn/end` 之后）编辑/拖动/删除，会借用被操作节点原来的
turn/step 坐标往日志尾部追写表面事件。典型现场（b1303b02）：

```
4112 step/end       (turn20 step53)
4113 turn/end       (turn20)          ← turn 已关闭
4114 session/end-seed
4115 system/message replace(20/53)    ← 插件在这里写编辑事件，全部非法
4116 system/message replace(20/53)
4117 assistant/message append(20/53)
4118 tool/result append(20/52)        ← 坐标还和同批其它事件矛盾
4119/4120 system/message replace
4121 tool/result append / 4122 assistant/message append
```

**经验 2**：日志是"只追加 + surface 折叠"的，**surface 的顺序改不了，只能遮蔽后重新追加**；
而"追加"永远落在末尾。想让节点出现在中间，只有"把这一段整体遮蔽再按目标顺序重放"一条路。
**经验 3**：写日志的合法性要在写入时判断，不能依赖加载期兜底——尤其坐标这种隐式约定。

## 三、修复已经坏掉的日志（tools/repair-migration.mjs）

### 3.1 方案对比

| 方案 | 结论 |
| --- | --- |
| 删除违规事件 + 重编号 | ❌ seq 必须 dense，删中间事件要重排全部后续 seq，并同步 `surfaceOp`/`sourceEventSeqs`/`shadowedSeqs` 等所有引用，风险极高 |
| 把事件搬进对应的开放 turn/step | ❌ append 形式的 `tool/result` 要求"结算已声明调用"，而它结算的调用早已结算过，搬进去依旧非法 |
| **降级为不透明可忽略事件** | ✅ 事件序号与帧结构完全不变，迁移器跳过关系校验 |

采用的降级写法：

```js
{ ...event, type: 'manual-context-orphan', ignorable: true }
```

迁移器对「v3 未知类型 + `ignorable:true`」的事件会做 `namespaceV3OpaqueEvent`：
改名成 `plugin:manual-context-orphan` 并**原样保留载荷与坐标**，从此不参与关系校验。
代价：这一次编辑不再生效（节点回到编辑前的表面状态），但消息内容、编辑记录文件都没丢。

### 3.2 三个必须记住的坑

1. **必须一次性降级全部违规事件。**
   只降级报错里提到的那个类型，会改变 surface 折叠结果，紧接着就报
   `compaction/summary shadowedSeqs do not name an exact current surface span`。
   正确姿势是每轮扫描**所有**违反 open turn/step 的事件再一起降级。
2. **别把 replace 形式的 `tool/result` 当违规。**
   它只要求"存在开放 turn"，坐标是老的（比如旧 turn1/step1）也合法。误判会导致大面积误改。
   判别式：`if (event.surfaceOp !== 'append') 只检查 state.turn !== null`。
3. **角色不匹配要就地改字段，别整条替换。**
   `message must have role "user"` 这类问题（老版本用 `user/message` 承载 `role:'assistant'`），
   v3 时代事件类型才是决定投影角色的字段，**直接把 `role` 改成 `user`** 就恢复了当年的显示与模型上下文，
   内容一字不丢；整条换成空消息会丢内容。

### 3.3 脚本工程化要点

- 校验必须走**真实加载路径**：`createSessionFormatCatalogWithChildren([]).createRestore(header, { recovery:'recoverable', validation:'transformed' })`
  → `decodeRow` × N → `finish()`，再补一个 `validateStoredEvents`。
  只用 `sessionFormatCatalog`（无 children 版本）会直接抛 "requires explicit historical child facts"，白忙一场。
- **第一帧必须恰好一行 header**；保留原有帧划分，只重压缩内容变化的帧。
- 先备份 `.corrupt-bak` → 写盘 → 重新读取再校验 → 失败自动还原。
- 默认 dry-run，`--apply` 才落盘。

命令：

```powershell
node tools/repair-migration.mjs                       # 预览
node tools/repair-migration.mjs --apply               # 落盘（自动备份 + 写后复验）
node tools/repair-migration.mjs --debug <单个文件>     # 看每轮降级了哪些 seq
```

## 四、插件侧的根治：守卫 + 排队

### 4.1 生命周期守卫

`history.js` 新增 `openCoordinates(session)`：扫一遍事件流算出当前开放的 turn/step 与下一个可用编号。
所有写日志的路径（编辑/删除/重排/重放/追加/遮蔽）在写入前调用 `writePosition(session)`：

- 拿不到开放 turn/step → 抛 `SessionWritePendingError`（`code = 'session-write-pending'`）
- **坐标一律用当前开放坐标，绝不抄原节点**（同批事件坐标互相矛盾正是坏日志的来源）

### 4.2 空闲写入 → 排队 → `agent/request` 应用

| 环节 | 位置 | 说明 |
| --- | --- | --- |
| 入队 | `http.js` 的 `handlePost` | 捕获 `session-write-pending`，写进 `$DSH_HOME/manual-context-edits/<sessionId>.queue.json`，返回 `{ok:true, queued:true}` |
| 应用 | `index.js` 的 `agent/request` 钩子 → `http.js applyQueuedOperations` | 此时 `step/start` 已写入、请求尚未组装，是**唯一合法的写入窗口** |
| 提示 | `client.js readJson` | 右下角提示「改动已排队，将在下一次请求组装时自动应用」 |

**关键事实（踩过）**：

- `agent/pre-step` **不能**作为写入窗口：它发生在 `turn/start` 之后、`step/start` **之前**，那时没有开放 step。
- `agent/request` 是 waterfall，payload 只有 `{ turn, step, signal }`，**没有 agent/sessionId**。
  于是 `applyQueuedOperations` 的做法是：遍历所有有队列文件的会话，用 `openCoordinates` 判断谁现在真的开着 step，谁开放就应用谁。
- 队列里的 `op`/`sessionId` 才是权威：注入类操作排队时只带了 payload 正文，
  应用时要 `Object.assign({}, operation.payload, { op: operation.op, sessionId })` 补回去（否则报"未知操作: "）。
- 同一会话反复入队要幂等：pre-step 每轮都会触发，入队前先看队列里有没有同类操作。

### 4.3 工具轨迹不能重放（重要）

`tool/call` **不是表面事件**，不在 surface 上。重放表面节点时天然缺它，于是：

- 重放 `tool/result` → `tool/result X has no advertised tool lifecycle`
- 重放含 `tool-call` 块的 `assistant/message` → 声明了没人结算 → `step/end leaves unresolved tool call`

结论：**编辑/重排遇到工具轨迹必须拒绝**（提示改用「删除」）。这比"写出去、下次打不开"好得多。

### 4.4 v4 原生形状适配

- **来源归属**：v4 拒绝裸 `kind:'plugin'`（`assertV4SourceRowAdmission`）。
  统一写提升后的生产者 kind：`plugin:@dsh-external/manual-context`
  （迁移器对未知 v3 plugin 名的映射结果就是这个形状，v3/v4 都合法）。
- **tool/result**：v4 要求一等 `role:'tool'` 消息 + 顶层 `toolCallId` + `source.kind:'tool'`，
  且内容不能是 `tool-result` 包装块；v3 仍是 `role:'user'` + 包装块。
  按 `session.header.version` 分叉（拿不到就当 3，保持兼容）。

### 4.5 顺手发现的两个坑

- **重放/重排不能换 `message.id`**：原实现用 `manual-context-move:<uuid>` 生成新 id，
  导致"节点身份"丢失——后面做幂等同步时完全认不出旧节点（见第六节）。
  现在改为**保留原 message.id**。
- **空内容的 `user/message` 仍会投影**（`deriveEventMessage` 只对 system/developer/assistant 返回 null），
  所以"删除一条消息"不能用空 user 消息，必须用**空 system/message**遮蔽。

## 五、四项新功能的实现要点

### 5.1 手动上下文注入 = 历史编辑同款（surface 节点）

`inject.js` 重写为 `syncManualContext(ctx, sessionId)`：

1. `planTargets(cwd)`：把**启用**的条目按段展开成目标节点
   （`id = manual-context:<hash>[:<段号>]`，user 段正文包 `<dsh-manual-context …>` 标记）；
   tool 轨迹的 callId 在这里就定死（`manual-call-<hash>-<index>`，**跨条目共享 pendingCalls**，保证配对稳定）。
2. `manualContextNodes(session)`：扫 surface，取出 id 前缀命中的节点（id → seq）。
3. 差分：目标里没有的节点 → `deleteMessages` 遮蔽；当前没有的目标 → `appendMessage`。
   **内容变化天然表现为"旧 id 消失 + 新 id 出现"**，不需要单独写"更新"逻辑——这是 hash 放进 id 的好处。
4. 位置：`desiredOrder` = [系统头, weight≤0 的目标（权重降序）, 其余历史, weight>0 的目标（权重降序）]，
   与当前顺序不一致才调用 `reorderMessages`。

**经验**：把"内容 hash"编进节点 id，同步就退化成集合差分，幂等性自然成立。

### 5.2 保存后不跳到系统上下文

`loadHistory` 原本会把选不中的 `selectedSeq` 回落成列表第一条（system/message）；
保存/删除/重排后旧 seq 已不在 surface 上，于是就"跳"了；排队响应没有 `replacedSeq` 时会永久停在那里。
修法：**已选中就保持不动**，替换成功时再用 `replacedSeq` 跟到新节点。

### 5.3 注入开关与权重

- frontmatter 新增 `enabled`（`false` 或 `disabled: true`）、`weight`（数字，默认 0）。
- `weight <= 0` → 系统提示词正下方；`weight > 0` → 正常对话最后面，**权重越大越靠前**。
- 面板把列表拆成两个分区，每行一个启用勾选框 + 权重输入框；拖拽跨区/区内排序后，
  自动按新顺序重写权重（上区 `0,-1,-2…`；下区 `m…1`），保证"看到的顺序 = 权重的语义"。

### 5.4 对话导出 / 导入

- 导出：`GET ?op=export-session` → `{ format:'dsh-manual-context/session-export', version:1, session, messages[] }`，
  每条消息带 `id/kind/role/text/reasoning/blocks/parts/manual`。
- 导入：`POST {op:'import-session', messages}` → **按 `message.id` 去重后追加**到当前会话末尾（幂等导入）。
  既接受导出文件本身，也接受裸的 `messages` 数组。

## 六、踩坑速查表

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| 只降级报错提到的类型 | 修完立刻报 `compaction/summary shadowedSeqs …` | 一次性降级**所有**违反 turn/step 的事件 |
| 用无 children 的 catalog 校验 v3 | `requires explicit historical child facts` | 用 `createSessionFormatCatalogWithChildren([])` |
| 修复改的是数组副本 | 落盘后校验失败（内容没变） | 修的是 `entries[i].line`，不是 `lines[i]` |
| 重放换 `message.id` | 同步不幂等、节点反复重建 | 重放/重排保留原 id |
| 空 user 消息当"删除" | 模型上下文里多一条空用户消息 | 用空 `system/message` 遮蔽 |
| `agent/pre-step` 写日志 | v4 迁移报 not match an open turn and step | 只在 `agent/request` 写 |
| 队列应用报"未知操作: " | `operation.payload` 里没有 op | 应用时补 `{ op: operation.op, sessionId }` |
| 用 fs 改过文件再 `edit` | `file changed since it was read` | 先 `read` 一次再 edit |
| 在 run_code 里写含 `\n` 的字符串 | 落盘变成字面 `\\n`，frontmatter 解析失败 | 用 `String.fromCharCode(10)` 或数组 `join` |
| React state 插在中间 | 前端测试按下标取 state 全部错位 | 新 state **追加在最后** |
| 测试夹具没有开放 step | 守卫触发，测试全红 | 夹具补 `turn/start` + `step/start` 模拟"对话进行中" |

## 七、复用手册

**扫描所有会话能否加载**

```js
const { createSessionFormatCatalogWithChildren } = await import('@deepseek-ai/dsh-session-format-catalog')
const restore = createSessionFormatCatalogWithChildren([]).createRestore(header, {
  recovery: 'recoverable', validation: 'transformed',
})
for (const line of rows.slice(1)) restore.decodeRow(JSON.parse(line))
restore.finish()            // 迁移 + surface 折叠
// 再跑 validateStoredEvents 才是完整校验
```

**日志读取**：`.jsonl.zstd` 是分帧 zstd，用魔数 `28 b5 2f fd` 切帧，逐帧 `zstdDecompressSync`，
按行解 JSON；**第一帧恰好只装 header 一行**。

**判断一个事件是否合法**（v4）：见第二节表格；`tool/result` 要区分 append/replace。

## 七点五、升级 dsh 到 0.1.7-rc.1 后的「插件坏了」

现象：升级 dsh 后插件整个消失（面板入口没了、路由 404），但日志里看不到明显的插件报错。

排查链路（结论：**不是代码不兼容，是挂载点没了**）：

1. `profiles/web/cordis.patch.yml` 里的 `insert: manual-context` 还在，但
   `profiles/web/node_modules/@dsh-external/manual-context` **不存在**了 → 模块解析失败。
2. `profiles/web/node_modules/.modules.yaml` 显示 `nodeLinker: hoisted`，
   且 `hoistedLocations` 里从来没有本插件 —— 说明它**从来不是 pnpm 依赖**，而是手工 junction。
3. 插件管理器日志里有一次 `pnpm install`（安装另一个插件）。hoisted 模式下 pnpm 会
   prune 掉不在 lockfile 里的顶层包，**手工 junction 就此消失**。

对照检查（都通过，说明 rc1 没改插件 API）：

| 检查项 | rc1 结果 |
| --- | --- |
| `window.__ModuleLoader__.load({id, factory})` + `ctx.slots.inject/register` | 与官方模板 `skills/cordis-plugin-development/templates/decoration/client.js` 完全一致 |
| slot id `conversation.session.header.actions` / `sidebar.footer.action` | 仍被 `dsh-client-ui-conversation` / `dsh-client-ui-sidebar` 声明 |
| `agent/pre-step`、`agent/request` 钩子 | 仍在 `dsh-agent` 等包中广播 |
| `session.append(type, data, ...opts)`、`session.surface`、`deriveEventMessage` | 签名一致 |
| `webServer.register({kind, path, handler})` | 实现一致 |
| 会话格式 | 仍是 v4（包列表里没有 v4→v5） |

修复与防复发：

```powershell
node tools/relink.mjs            # 重建 junction（幂等，--dry-run 只看不动）
node tools/smoke-load.mjs        # 用 rc1 自带 cordis 冒烟加载宿主插件
```

**教训**：开发中的插件用 junction 挂载时，任何一次 `pnpm install` 都会把它清掉；
这类"插件整体消失且无报错"的问题，先查 `node_modules` 挂载点，再查代码兼容性。另外，
用 PowerShell 的 `Select-String` 搜 JS 源码时别用 `\"` 当转义（PowerShell 里它是字面反斜杠），
否则会得到"符号不存在"的假结论。

## 七点六、实测校准：v4 **不检查** turn 关系（推翻 4.1 的保守结论）

> ⚠️ **本节结论已作废（2026-09 更正）**：当时的实验用的是
> `validation: 'transformed'`，它只做物理解码 + 形状校验，**不跑 `Session.fromRestore`
> 的关系校验**，于是把 turn/step 约束整个漏掉了。同一份日志换成真实加载路径
> （`validation: 'current'`）会当场报 `assistant/message does not match an open turn and step`。
> 正确结论见「七点八」——**空闲时写入确实会让对话下次打不开**，
> 插件已经把空闲写入改成排队。

**起因**：用户问「刚创建新对话、还没发第一句话时，为什么不能注入上下文？」

**原来的判断**（本文 4.1 / 七点五）：表面事件必须落在开放 turn/step 内，否则会话打不开。
这个结论来自 **v3→v4 迁移器**的报错，但被过度推广成了「运行时也写不了」。

**实验方法**（`tools/experiment-turn-gate.mjs`）：拿一个真实 v4 会话的 header，
拼上合成事件，走 DSH **完整加载路径**：

```js
const restore = withChildren([]).createRestore(header, { recovery: 'recoverable', validation: 'transformed' })
for (const event of events) restore.decodeRow(event)
const artifact = restore.finish()
validateStoredEvents({ id, version: artifact.header.version, kind: 'jsonl', path: '' }, artifact.events, id)
```

**结果**（同一套路径，基线通过）：

| 写入的事件（全在 turn 之外） | 加载 |
| --- | --- |
| `user/message`（append） | ✔ |
| `assistant/message` 单块 / **多块（reasoning+text+tool-call）** | ✔ |
| 空内容 `system/message` 遮蔽节点（replace） | ✔ |
| `tool/result`（append） | ✔ |
| 只有 header 的空会话里写 `user/message` | ✔ |

**结论**：
- **v4 会话**：加载校验只查事件形状与会话角色，**不检查 turn/step 关系** —— 空闲时想写什么都能写。
- **v0–v3 会话**：加载时会跑 v3→v4 迁移，迁移器**才**检查生命周期 —— 写进去会让会话打不开。
- 实测还发现：真实会话开头是 `turn/start → step/start → user/message`，
  **系统提示词走 `request/header` 事件、根本不是 surface 节点**；
  surface 的第 0 个节点本来就是用户的第一句话。所以「新建对话时先注入」天然排在用户消息之前。

**落到代码上**：
| 改动 | 位置 |
| --- | --- |
| `writablePosition(session, kind)`：v4 空闲时用**日志里最后一次出现的 turn/step** 兜底，旧格式仍抛 pending | `src/history.js` |
| `syncManualContext` 逐条容错：写不进去的记 `deferred`，能写的先写 | `src/inject.js` |
| `desiredOrder`：只有第 0 个节点**确实是** `system/message` 时才把它当系统头保留 | `src/inject.js` |
| `status` 返回 `queued` / `canWrite` / `version`；面板轮询显示排队状态 | `src/http.js` / `src/client.js` |

**教训**：迁移器的约束 ≠ 运行时的约束。判断"能不能写"要用**最小可复现实验**走真实加载路径，
不要从一段报错外推成全局规则 —— 否则会做出用户能直接感觉到的、没必要的保守行为。

## 七点七、会话打不开（界面空白且无报错）的根因

**症状**：某个对话点开后**一片空白，前后端都不报错**。看起来像渲染问题，其实是**会话加载失败**。

**第一步取证**（不要猜）：把真实会话文件喂给 dsh 的完整加载路径 ——
`createRestore(header, { recovery:'recoverable', validation:'transformed' })` → `decodeRow` →
`finish()` → `validateStoredEvents`，错误立刻现形：

```
stored session "…" failed validation:
Error: session event at seq 6 message must have system-prompt source
```

注意错误在 `error.cause` 里：打印 `error.message` 只会看到 `failed validation:` 这句空壳。

### 根因

插件删除 / 重排 surface 节点时会写一条**空 system/message** 把原节点遮蔽掉。这一步的类型选择是被逼出来的：

- 遮蔽必须带 `sourceEventSeqs`，而 **只有 `system/message` 能带**。
  换成被遮蔽节点的同类型（例如 `assistant/message`）会被 v4 拒绝：
  `assistant/message embeds its source stream and cannot carry sourceEventSeqs`。
- 但 `system/message` 的来源**必须是 `system-prompt`**。旧版写的是 `plugin:@dsh-external/manual-context`。

**一条不合格 → 整份日志校验失败 → 整个会话打不开。**

### 两个反直觉之处

1. **它不会在写入时报错**。写入完全成功，问题要等下次**加载**才暴露，所以症状出现在"打开对话"而不是"编辑对话"。
2. **校验是全局的、不是逐条的**。一个 seq 上的一条消息就能让 3596 条事件的会话整个作废。
   这就是为什么修复必须"整份文件重写"，而检测必须"先跑真实校验器"，不能只看单个事件。

### 修法

只改 `source.kind` → `'system-prompt'`：内容仍为空、位置与遮蔽关系完全不变，模型看到的内容不变。
面板上的「修复对话」按钮（`src/repair.js`）就是这个逻辑的封装；命令行等价物是 `tools/fix-mask-events.mjs`。

### 顺带修掉的两处

- **排序不再搬动 system 节点**。重放 system/message 会改写它的来源 —— 等于再写坏一次。现在
  `desiredOrder` 只决定"手动上下文插在哪"，`reorderIfNeeded` 会二次确认，若这次排序会移动系统提示词就**直接放弃**。
- **注入内容版本升到 r3**。注入节点按内容哈希识别，升版本号 = 所有会话自动重新注入一次，
  旧节点进遮蔽、新节点落在系统提示词之后，历史遗留的顺序问题自愈。

### 教训（关于验证方式）

我上一轮用"合成的 header + 合成事件"跑校验，恰好绕过了这条来源检查，于是错误地宣布"没问题"。
**验证会话格式这类东西，必须拿真实会话文件跑真实加载路径**，自造的样本会漏掉真正的约束。

## 七点八、surface 首节点与 turn 内约束：一次「修好了又坏」的完整复盘

**症状**：用户报 `stored session "…" is corrupt: system/message requires a protected first
surface head`，点「修复对话」却说「扫描 92 个对话没有可修复的」。

### 两件事同时错了

1. **修复的判据太窄**：旧修复器只认「遮蔽事件来源是插件」这一种坏法，
   而这次的坏法是 surface 结构问题，完全不在它的判据里 —— 所以它诚实地报告「没有可修复的」。
2. **验证方式不对**（就是七点六的坑）：旧验证脚本一律用 `validation: 'transformed'`，
   它不跑关系校验。**用它验证等于没验证** —— 会话在真实加载时照样打不开。

### 三条此前不知道的 v4 硬规则

在 `@deepseek-ai/dsh-session-format-v3-to-v4/lib/index.js` 的 `Relationships.foldSurface`
与 `accept` 里读到的：

1. **surface 的第一个节点必须是 `system/message`**。
   `system/message` 到达时若 surface 非空且 `protectedHead` 还没定，直接抛
   `system/message requires a protected first surface head`。
2. **除了 `user/message`，其它 surface 类型都要落在打开的 turn+step 里**：
   - `system/message` / `developer/message` / `assistant/attempt`：`accept` 开头就 `requireStep`；
   - `assistant/message` / `tool/call` / **追加形式**的 `tool/result`：走 `tool()` → `requireStep`；
   - **替换形式**的 `tool/result` 只走 `requireTurn`（turn 内即可，不要求 step）。
3. **遮蔽事件的 source 必须是 `system-prompt`**（只有 `system/message` 能带
   `sourceEventSeqs`）。这条是七点七留下的。

### 根因：插件趁会话空闲时写节点

```
seq 3  user/message   append   id=manual-context:r3:…     ← 空闲时注入，成了 surface 第一个节点
seq 5  turn/start
seq 7  step/start
seq 8  system/message replace[3]  （空遮蔽）
seq 9  system/message replace[8]  ← 真正的系统提示词
```

运行时一切正常，**下次加载就整份被拒**（规则 1）。同型坏法还有：助手段 / 工具段落在
`turn/end` 之后写入（规则 2），以及遮蔽事件来源是插件（规则 3）。92 个会话里 6 个中招。

### 修法（`src/repair.js`）

| 坏法 | 修法 | 为什么不会改变模型看到的内容 |
| --- | --- | --- |
| 注入节点压在系统提示词前面 | 把它改写成**带 `ignorable` 的未知事件**（`x-manual-context/orphan`），彻底退出 surface 折叠；再把因此失去遮蔽对象的空 `system/message` 改成 `append` | 这些节点**本来就已经被后续的空 system/message 遮蔽掉**，模型根本看不到 |
| 注入段落在 turn 之外 | 降级成 `user/message`（data 从 `{turn,step,message}` 摊平成 message，role 改 `user`） | 同样已被遮蔽；遮蔽关系与内容都保留 |
| 遮蔽来源是插件 | 只改 `source.kind` | 内容为空、位置不动 |

**两条安全绳**：

- 每一步改完都用**真实加载路径**重新校验：
  `createSessionFormatCatalogWithChildren([]).createRestore(header, { recovery: 'recoverable', validation: 'current' })`
  + `decodeRow` + `finish()`，通不过就整份放弃；拿不到 dsh 的格式包只报告、不写盘。
- 凡是「链条里出现真实内容」就拒绝动手，返回原因而不是硬改。
  例：`tool/result` 找不到配对的 tool/call（`not-started error requires an object`）会如实
  报「暂不支持」。

### 结果

92 个会话里 5 个修好并通过真实校验，复扫只剩 1 个（上面那类「暂不支持」）。
用户报的那个会话一次修好。

### 写入侧的根治

**不要自己判断时机 —— 直接复用历史编辑那条已经验证过的链路。**

历史编辑（删除 / 重排）之所以一直没问题：`deleteMessages`/`reorderMessages` 内部走
`writePosition`，会话空闲（没有开放 turn/step）时抛 `SessionWritePendingError`；HTTP 层
把它排队，下一轮 `agent/request`（step 已打开）再原样重放。

手动上下文现在完全一样：

- `writablePosition` **删掉了「v4 回退到日志里最后一次 turn/step」的放行** —— 那是错的，
  v4 一样校验 turn 关系，放行只会写出打不开的日志；`user/message` 也一视同仁
  （它虽然不要求 turn/step，但空闲时写进去会成为 surface 首节点，同样是坏日志）。
- `syncManualContext` 里那段自己写的 `idle` 特判删掉了。它的害处很隐蔽：空闲时返回
  `idle` 而**不抛错**，于是 `applyQueuedOperations` 认为「应用成功」，把队列清空 ——
  用户看到「排队中」消失，对话里却什么都没注入，而且无迹可查。

顺带把 `applyQueuedOperations` 的错误处理改对了：**任何写不进去的操作都留在队列里**
（超过 5 次才放弃），并把每次尝试写进 `$DSH_HOME/manual-context-edits/apply.log`。
以前非 pending 的错误被直接丢掉，正是「排队消失但没注入」的另一半原因。

### 教训

1. **验证必须走真实加载路径**（`validation: 'current'`）。`'transformed'` 只适合检查
   「解码能不能过」，不能用来判断「会话能不能打开」——七点六就是这么被误导的。
2. **「扫描 N 个会话没有可修复的」不等于没问题**，也可能只是判据太窄。
3. **修复器要自带校验**：改完用真实加载校验重跑，通不过就不落盘 —— 否则修坏比不修更糟。

## 八、遗留与后续

- 权重 ≤0 的条目要"插到系统提示词正下方"而对话已经很长时，重排要遮蔽+重放，
  单段超过 `REPLAY_LIMIT = 300` 会放弃并记警告；后续可考虑"在对话开始前抢占位置"的写入策略。
- 工具轨迹（`tool/result`、`tool-call`）目前只能删除、不能编辑/重排；
  若将来要支持，必须整组重写：`assistant/message(声明新 callId) → tool/call → tool/result`。
- 插件写入仍然依赖"当前会话内存里已是 v4 表示"；如果 DSH 再升级格式，需重新核对
  `assertV4*Admission` 系列规则（形状适配集中在 `history.js` 的 `assertWritableEvent` / `appendMessage`）。
