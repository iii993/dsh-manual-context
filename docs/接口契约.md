# 接口契约：`/manual-context` 宿主 HTTP 接口

> 本文是 **`src/http.js` 的对外契约**（谁调用、传什么、拿回什么、什么情况下排队）。
> 落地位置都标了 `文件:行号`；行号对应本次审查时的快照。
> 相关文档：`docs/项目说明.md`（模块划分 / 数据流 / 会话格式约束 / 陷阱清单）、
> `docs/会话格式与手动上下文-经验总结.md`（历史事故复盘）。
>
> **审查结论（重要）**：第 7 节列出 7 处契约不自洽或歧义，其中 B1/B2 会写出打不开的会话日志。
> 改接口前先读第 7 节。

```jsonc
// 成功
{ "ok": true, /* op 自己的字段 */ }
// 失败（注意：HTTP 状态码仍是 200）
{ "ok": false, "error": "人类可读中文原因" }
```

| 情况 | HTTP | body | 位置 |
| --- | --- | --- | --- |
| 业务成功 | 200 | `{ok:true,…}` | `src/http.js:40`, `src/http.js:52` |
| 业务失败（任何 throw） | **200** | `{ok:false,error}` | `src/http.js:56-59` |

空 body → 抛错；非 JSON → 抛错；`ok === false` → `throw new Error(value.error)`；
`queued === true` → 弹一次「改动已排队」的提示条（**不是错误**，见第 2 节）。

## 2. 排队（session-write-pending）语义

这是最容易误判的一环：**「写不进去」不等于「失败」，而是「已排队，下一轮自动应用」。**

### 2.1 什么时候会排队

会话当前**没有开放的 turn/step**（上一次 `turn/end` 之后，或新会话还没说话）时，
任何表面事件写入都会抛 `SessionWritePendingError`（`code === 'session-write-pending'`）：

- 定义：`src/history.js:36-42`
- 抛出点：`writablePosition` → `writePosition`（`src/history.js:799-827`）
- HTTP 兜底：`handlePost` 捕获后**把整个 payload 入队**并返回
  `{ok:true, queued:true, message}`（`src/http.js:428-437`）

### 2.2 队列文件与流水

| 项 | 位置 |
| --- | --- |
| 队列文件 | `$DSH_HOME/manual-context-edits/<encodeURIComponent(sessionId)>.queue.json`（`src/history.js:89-91`） |
| 队列形状 | `{ sessionId, operations: [{ op, payload, requestedAt, attempts? }], updatedAt }`（`src/history.js:94-127`） |
| 空队列 | 直接删除文件（`src/history.js:105-115`） |
| 应用流水 | 同目录 `apply.log`，逐行记录「完成 / 重试 / 放弃 / 跳过」+ 原因（`src/history.js:49-63`） |
| 入队来源① | 任何带 `sessionId` 的写操作抛 pending 时（`src/http.js:432-435`） |
| 入队来源② | `sync-context` 返回 `deferred > 0` 时（`src/http.js:319-323`） |
| 入队来源③ | `agent/pre-step` 每 turn 首步（`step === 1`）塞一条 `sync-context`（`src/inject.js:421-438`） |
| 应用时机 | `agent/request` 钩子 → `applyQueuedOperations`（`src/index.js:27-34`, `src/http.js:512-549`） |

### 2.3 应用规则（`applyQueuedOperations`，`src/http.js:512-549`）

1. 只遍历**磁盘上有队列文件**的会话（`listQueuedSessions`）；会话不在内存里 → 记 `apply.log` 后跳过。
2. 会话当前**没有开放 turn+step** → 记日志后整批跳过（**这个门槛是本次事故的关键，见 7.B1**）。
3. 逐条重放：`runOperation(ctx, { ...operation.payload, op, sessionId })` —— 队列里的 `op`/`sessionId` 是权威。
4. 单条失败：**留在队列里**并 `attempts+1`；`attempts > 5` 才放弃（丢弃并记日志）。
5. 每条重放结果都写进 `apply.log`。

### 2.4 幂等性

| 操作 | 重复排队 / 重复执行会不会翻倍 | 依据 |
| --- | --- | --- |
| `sync-context` | 不会。`pre-step` 与 HTTP 层各自做了「队列里已有就不再加」 | `src/inject.js:430-433`, `src/http.js:320-322` |
| `import-session` | 不会。按 `message.id` 去重（每次重放都重算 existing 集合） | `src/http.js:727-731`, `src/http.js:754-757` |
| `import-entries` | 不会（同名文件直接判「条目已存在」→ 计入 skipped） | `src/store.js:426`, `src/http.js:870-882` |
| `append-message` | **会翻倍**。没有 id 去重，也没有队列去重；空闲时点两次「新增」= 排队两条 | `src/http.js:292-304`, `src/history.js:859` |
| `save-edit` / `delete-*` / `reorder-messages` | 队列重复 = 重放两次；第二次通常因目标已变而失败（留在队列，5 次后丢弃） | `src/http.js:526-544` |
| `edit-pending` / `drop-pending` | **不幂等**：`queueIndex` 是位置下标，重试可能命中别的操作 | 见 7.B4 |

> `sync-context` 的去重是「两个入口各自判断」，所以理论上仍可能同时排进两条
> （`src/http.js:320` 会先查一次，实际概率极低）。

## 3. GET 操作（`handleGet`，`src/http.js:117-199`）

`op` 缺省为 `status`（`src/http.js:118`）。未知 op → `{ok:false,error:'未知操作: x'}`（`src/http.js:196-197`）。

### 3.1 `op=status`

| 入参 | 必填 | 说明 |
| --- | --- | --- |
| `sessionId` | 否 | 省略 / 空串时只列目录与条目，不返回会话相关字段 |

返回（`src/http.js:122-154`）：

| 字段 | 类型 | 说明 | 前端用途 |
| --- | --- | --- | --- |
| `dirs` | string[] | 该 cwd 要扫描的根目录绝对路径 | — |
| `roots` | `{index,path,label}[]` | 可写根目录清单 | 新建 / 导入的目录下拉（`client.js:1522-1528`） |
| `home` | string | `$DSH_HOME` | 展示 |
| `cwd` | string 或 null | 会话工作区 | — |
| `entries` | object[] | `listEntries` 结果（id/name/role/enabled/weight/hash/bytes/mtime…） | 条目列表 |
| `injected` | `{id,name,role,inContext}[]` | 每条是否已在模型可见历史里 | 「未注入」徽标 + 打开面板自动补同步（`client.js:376-385`） |
| `edits` | object[] | 该会话的编辑档案 | 「已编辑」标记 |
| `queued` | number | 队列长度 | 顶部「排队中：N 项」（`client.js:1497-1501`） |
| `queue` | `{op,payload}[]` | 队列明细（**不含 queueIndex**，明细要用 `history` 的 `pendingAdds`） | 调试 |
| `canWrite` | boolean | `turn!==null && step!==null` | 「当前会话已可立即写入」（`client.js:1500`）——**语义不准，见 7.B5** |
| `version` | number 或 null | `session.sessionVersion ?? session.header?.version` | 版本显示 |
| `inject` | boolean | 注入总开关 | 「注入：开 / 关」按钮态（`client.js:1478-1481`） |
| `settings` | `{inject}` | `readSettings()` 原样 | — |

轮询：面板停在「手动上下文」页时每 2500ms 调一次（`src/client.js:359-363`）。

### 3.2 `op=file`

| 入参 | 必填 | 返回 |
| --- | --- | --- |
| `sessionId`, `id` | `id` 必填 | `{ok:true, entry}` —— `readEntry` 的完整结果（含 `content` / `body` / `meta` / `segments` / `segmentRoles`） |

错误：`缺少 id`（`src/http.js:157`）；条目不存在 → `手动上下文条目不存在: <id>`（`src/store.js:340`）。

### 3.3 `op=history`

| 入参 | 必填 |
| --- | --- |
| `sessionId` | **是**（缺失 → `缺少 sessionId`） |

返回 = `listHistoryMessages` 的展开（`src/http.js:164-169`, `src/history.js:274-324`）：

| 字段 | 说明 |
| --- | --- |
| `nodes` | 当前 surface 的 seq 数组 |
| `messages[]` | `{seq,type,kind,label,role,time,text,reasoning,hasReasoning,blocks,parts,toolCalls,toolCallId,edited,editedAt,pendingDelete,protected}` |
| `edits` | 编辑档案 |
| `queued` | 队列明细（含 `payload`） |
| `pendingAdds` | **「将被添加」区块的数据源**：`[{queueIndex,source,kind,text,reasoning?,toolName?,toolInput?,entryId?,entryName?,editable}]`（`src/http.js:449-504`） |
| `cwd` | 会话工作区 |

前端依赖：`protected`（系统头不可编辑 / 不可拖）、`edited`（「已编辑」徽标）、
`pendingDelete`（「将被删除」徽标）、`parts`（片段行）、`toolCallId`（导出配对）。

### 3.4 `op=export-session`

| 入参 | 必填 |
| --- | --- |
| `sessionId` | **是** |

返回 `{ok:true, ...exportSession}`（`src/http.js:171-174`, `src/http.js:566-597`）：

```jsonc
{
  "format": "dsh-manual-context/session-export",
  "version": 1,
  "exportedAt": "ISO 时间",
  "session": { "id": "session-…", "cwd": "…" },
  "messages": [ { id, seq, type, kind, role, time, text, reasoning, blocks, parts, toolCallId, manual, protected } ]
}
```

- `manual`：`message.id` 以 `manual-context:` 开头（`src/http.js:586`）。
- `toolCallId`：**v4 一等 `tool/result` 的配对 id 只在 `message.toolCallId` 上**，必须导出，
  否则导回去工具返回变孤儿（`src/http.js:583-585`）。
- `id` 可能为 `null`（`messageIdAt` 取不到 id 时，`src/http.js:555-560`）→ 该条导入时**没有 id 去重**。

### 3.5 `op=workspaces`

入参：无（`sessionId` 只用于回显 `cwd`）。
返回 `{ok:true, workspaces:[{cwd,title,active}], cwd}`（`src/http.js:175-179`, `src/http.js:78-101`）。

- 数据源 = 活跃会话的 `session.header.cwd`（`active:true`）+ `$DSH_HOME/storages/workspace.json` 的 `projects[*].path`。
- `title` 可能为 `null`；索引读不到时只返回活跃会话（不报错）。
- 前端：导入面板的「工作区」下拉 + 默认值（`client.js:868-882`）。

### 3.6 `op=sessions`

返回 `{ok:true, sessions:[{id,status,cwd,title}], current}`（`src/http.js:180-195`）。
侧边栏入口拿不到 slot 的 sessionId，用它挑一个会话（`client.js:449`）。

除 `repair-sessions` 外全部**同步**执行。未列出的 op → `未知操作: x`。

| --- | --- | --- | --- | --- |

### 4.1 条目文件类

- **`save-file`**（`src/http.js:215-225`）：`payload.meta` 是对象时走 **JSON 模式**
  → `writeEntryMeta(id, meta, body)`（`src/store.js:397-400`）；
  否则走 **文本模式** → `writeEntry(id, content, role)`（`src/store.js:406-414`）。
  错误：`缺少 id`；条目不存在；`content 必须是字符串`；超过 `MAX_FILE_BYTES = 512 KiB`（`src/store.js:21`, `src/store.js:411`）。
- **`create-file`**（`src/http.js:226-231`）：`root` 是**根目录下标**，缺省 0；
  文件名由 `sanitizeName` 校验（不许路径分隔符、不许点开头、无扩展名补 `.md`，`src/store.js:453-462`）；
  重名 → `条目已存在: <name>`。返回 `{entry}`，前端拿 `entry.id` 设为选中（`client.js:929`）。
- **`save-segments`**（`src/http.js:232-240`）：前端把整个片段数组发回来，
  宿主用 `segmentsToBody` 重组正文（`src/store.js:233-256`）—— **解析 / 重组规则只存在 store.js 一处**。
- **`delete-files`**（`src/http.js:277-291`）：逐条容错，返回 `removed` 与 `failed`；单条失败不中断整批。

### 4.2 会话编辑类

- **`save-edit`**：`content` 数组存在时走 JSON 模式（`asBlocks`），否则文本模式；两者都给时 `content` 优先
  （`src/history.js:700-729`）。
  - 返回 `replacedSeq`：前端据此把选中项切到新节点（`client.js:976`）。
  - 错误：`该消息内容已变化，请刷新后重试`（`expectedText` 不匹配）、
    `该消息已不在当前模型可见上下文中（可能已被压缩）`、
    `系统提示词由 Harness 在每轮请求前重新渲染，无法被替换改写`、
    模型输出重放上限 `REPLAY_LIMIT = 2000`。
  - **排队语义的例外**：不走 `appendMessage` 的替换路径（`replaceInPlace`）**没有生命周期守卫**，
    空闲时会直接写日志 —— 见 7.B2。
- **`delete-messages`**：用空内容 `system/message` 遮蔽（`blankOut`, `src/history.js:542-558`）；
  `surface[0]` 若是系统提示词则跳过（进 `skipped`）。返回 `{deleted,skipped}`。
- **`delete-part`**：删单个 content 块；删空时自动转整条删除，返回 `mode:'message'`；
  否则 `mode:'part'` 且带新的 `blocks`（`src/history.js:1048-1074`）。
- **`reorder-messages`**：目标顺序 → 最长公共前缀原地不动 + 其余「遮蔽后按序重放」；
  返回 `replaced` 映射（旧 seq → 新 seq）（`src/history.js:1088-1144`）。
  未知 / 重复的 seq 被忽略，漏掉的按原顺序补在末尾；顺序没变则 `{moved:0}` 不写事件。
- **`append-message`**：`kind ∈ user|assistant|reasoning|tool-call|tool-result`；
  `blocks` 通道用于「思维链 + 正文 + 工具调用」合并成**一条** assistant 消息（`src/history.js:873-918`）。
  - `tool-result` 未给 `callId` 时自动接上「最近一条已声明、还没返回」的工具调用；
    找不到 → 抛错（`src/history.js:981-990`）。
  - **`blocks` 通道里的 `tool-call` 不会补 `callId`** → 见 7.B3。

### 4.3 注入类

- **`sync-context`**（`src/http.js:314-324`）：调 `syncManualContext`（`src/inject.js:283-361`）。
  - 返回 `added / removed / reordered / total / deferred / warnings`；总开关关闭时额外带 `disabled:true`。
  - `warnings` 是「没法安全注入的段」的可读原因（例如没有配对工具调用的 tool-result 段）。
  - `deferred > 0` 时 HTTP 层**再排一条 `sync-context`**（若队列里还没有）。
  - **没有 `idle` 字段** —— 前端在 `client.js:634` 读它，是死分支，见 7.B5。
- **`set-inject`**（`src/http.js:377-390`）：写 `$DSH_HOME/manual-context/settings.json`，
  并在有会话时顺手同步一次（把已注入节点遮蔽掉）。返回 `{inject, sync}`；
  `sync` 可能是 `{error}`（同步失败不影响开关本身）。
- **`agent/pre-step` / `agent/request`**：不是 HTTP 接口，但契约上与排队强相关 ——
  pre-step **只排队**（`src/inject.js:421-438`），request **才应用**（`src/index.js:27-34`）。

### 4.4 排队编辑类

- **`edit-pending`**（`src/http.js:337-376`）：只接受 `op === 'append-message'` 的队列项
  （否则提示「请到『手动上下文』页改条目本身」）；按「思维链 / 正文 / 工具调用」组装 `blocks`，
  再回写队列（不写日志）。
- **`drop-pending`**（`src/http.js:325-336`）：按下标删掉队列中的**任意一条**操作，返回剩余条数。
- 两者的 `queueIndex` 就是 `loadQueue()` 数组下标，来源是 `history.pendingAdds`
  （`src/http.js:449-504`）；**一次 `sync-context` 会展开成多行、共用一个 queueIndex**
  （`src/http.js:493`，前端注释 `client.js:1975`）。

### 4.5 导入类

- **`import-session`**（`src/http.js:394-399` → `importMessages`, `src/http.js:724-809`）：
  - 三条铁律：逐条容错 / 如实反馈（`skippedReasons`） / 工具调用先落、工具返回后落。
  - 系统提示词**不导入**，原因写进 `skippedReasons`（`src/http.js:617-624`）。
  - 会话空闲时：`importMessages` **原样抛出 pending**（`src/http.js:770-772`），
    由 `handlePost` 把**整批**入队并返回 `{ok:true,queued:true,message}`。
    因此该 op **有两种互斥的返回形状**（结果 / 排队），前端两处都判（`client.js:896-905`）。
  - 重复 id → 进 skipped，理由「这条消息已经在会话里了（按 message.id 去重）」。
- **`import-entries`**（`src/http.js:400-411` → `importEntries`, `src/http.js:848-885`）：
  - 目标目录：优先 `payload.cwd`，否则会话 cwd；两者都没有 → 抛「缺少工作区目录」。
  - `rootIndex` 缺省 0；`format ∈ md|markdown|txt|text`（缺省 md，**前端不传**）。
  - 文件名净化：只取最后一段路径、替换 Windows 非法字符、去首尾点 / 空格（`src/http.js:821-832`）；
    净化后为空 → 跳过并给原因。
  - 返回 `{cwd, written, skipped}`：**`written` 是「条目 id 数组」**，`skipped` 是
    `[{name,index,reason}]` 数组 —— 与 `import-session` 的 `skipped`（数字）**同名不同类型**，见 7.B7。

### 4.6 修复类

- **`repair-capability`**：`{supported}` —— 当前环境能不能拿到 zstd 与 dsh 格式包。
- **`repair-sessions`**（**异步**，在 `handlePost` 里特判，`src/http.js:418-427`）：
  入参 `{apply?:boolean（默认 true）, sessionId?:string}`；带 `sessionId` 时只处理那一个
  （面板的「修复此对话」），不带则全扫（「修复全部」）。
  运行中的会话会被跳过。落盘前用 dsh 真实加载路径校验。

## 5. 事件形状契约（写入前自检）

写入会话日志的任何事件都先过 `assertWritableEvent`（`src/history.js:381-431`），
它对应 dsh 的 `assertMessageEventShape`；**不合规就抛错，绝不落盘**。

| 事件类型 | message.role | source | 其它 |
| --- | --- | --- | --- |
| `user/message` | `user` | kind 非空（本插件写 `plugin:@dsh-external/manual-context`） | `data` 直接是 message |
| `assistant/message` | `assistant` | `model` + `provider`/`model` | 需 `turn`/`step`/`stream`；**不能带 `sourceEventSeqs`** |
| `tool/result` | v3: `user` / v4: `tool` | `tool` + `callId` | v4 需 `toolCallId === source.callId` 且不许再嵌 `tool-result` 块；v3 恰好一个包装块 |
| `system/message` | `system` | 遮蔽用 `system-prompt`；普通替换用 `plugin:@dsh-external/manual-context` | 见下面的首节点保护 |

**surface 首节点（`protectedHead`）**：dsh 折叠时若 surface 非空、`protectedHead` 还没定，
再来一条 `system/message` 就直接拒：`system/message requires a protected first surface head`。
本仓库的等价模型见 `src/repair.js:242-247`（7.B1 就是这条约束没被写入门槛）。

## 7. 契约不自洽 / 歧义清单（本次审查结论）

> 按严重程度排序。**B1 / B2 会写出打不开的会话日志**（本次事故那一类），其余是接口卫生问题。

### B1（严重）排队应用的时机门槛只有「turn/step 开着」，缺「surface 首节点已是 system/message」

| 位置 | 假设 |
| --- | --- |
| `applyQueuedOperations` `src/http.js:520-524` | 只要 `openCoordinates` 的 turn/step 非空就重放 |
| `writablePosition` / `writePosition` `src/history.js:799-827` | 同上，仅此一条 |
| dsh 折叠规则（仓库内等价模型 `src/repair.js:242-247`） | surface 非空且 `protectedHead` 未定时再写 `system/message` → 整份日志被拒 |

`agent/request` 发生在 `step/start` 之后、**系统提示词写进 surface 之前**。
新会话此刻 turn/step 已开、surface 还是空的 → 排队的 `import-session` / `sync-context`
把 `user/message` 写成 surface 首节点 → 系统提示词随后写入 → 下次加载报
`system/message requires a protected first surface head`（本次 `session-b526d0d4` 事故）。
同一份代码里 `src/inject.js:230-245` 还写着「真实会话里系统提示词不是 surface 节点」，
与 `src/repair.js:242-247` 的规则相反 —— 两处假设互斥。

### B2（严重）`replaceInPlace` 是唯一没有任何时机守卫的写入路径

`replaceInPlace`（`src/history.js:561-590`）**不调用** `writablePosition`，
`applyEdit`（`src/history.js:732-734`）与 `deletePart`（`src/history.js:1067-1069`）
在目标不是 `assistant/message` 时直接走它。后果：

- 空闲时编辑**用户输入**：写出 `user/message` 替换事件（payload 不含 turn/step）→ 立即落盘、不排队；
- 空闲时编辑**系统消息 / 工具返回**：payload 抄原事件的 turn/step → 表面事件落在 turn 之外 →
  下次加载被 v4 迁移器拒（`tool/result does not match an open turn` 一类）。

同一次审查里，`appendMessage`（`src/history.js:855`）、`blankOut` 的三个调用点
（`src/history.js:652/1025/1110`）都走了守卫 —— 只有这一条没有。
测试也没有覆盖空闲 `save-edit`（`tests/host.test.mjs:894` 只测了 `reorder-messages`）。

### B3（中）`blocks` 通道里的 `tool-call` 不保证有 `callId`

- 宿主：`src/history.js:897` 写 `id: block.callId`；`blocks` 由调用方给时可为空 → `undefined` 被 JSON 丢弃。
- 两个调用方都不给：`edit-pending` `src/http.js:361`、前端「＋新增」`src/client.js:1085`。
- 唯一会补齐的是导入通道 `importedBlocks` `src/http.js:640-648`（`manual-call-<uuid>`）。
- 下游要求非空：`lastUnansweredCallId` 只认 `typeof block.id === 'string'`（`src/history.js:609`）。
  结果：面板新增的「工具调用」拿不到 id，紧随其后的「工具返回」永远配不上对 →
  `appendMessage` 抛「没有已经声明、还没返回的工具调用」。
  **同一个 `blocks` 字段，导入路径必有 callId、面板路径必无** —— 契约必须二选一。

### B4（中）`queueIndex` 是位置下标，没有版本号

- 前端每 2.5s 轮询 `status`（`src/client.js:359-363`），拿到 `pendingAdds[].queueIndex` 后才点「编辑 / 丢弃」；
  队列在此期间变化（例如 `agent/request` 应用了前一条）→ 下标指向**另一条**操作。
- `drop-pending` 不校验操作类型，会删掉该下标上的**任意** op（包括 `import-session`、`save-edit`）
  （`src/http.js:332-335`）；`edit-pending` 只拒绝非 `append-message`（`src/http.js:345-347`）。
- 一次 `sync-context` 展开成多行共用一个下标（`src/http.js:493`），所以「取消同步」会连带取消整批 ——
  这是当前**有意**的行为（前端标题写明），但契约上没有表达出来。
- 两个 op 都**不可安全重试**（无幂等 token）。建议：队列项加稳定 id，接口改用 id 定位。

### B5（中）`sync-context` 不返回 `idle`，`canWrite` 也不表达真实可写条件

- 前端读 `value.idle`（`src/client.js:634-642`）决定「空闲」文案，宿主**从不返回该字段**
  （`src/http.js:314-324`）。于是新会话同步时会走 `deferred > 0` 分支，
  提示「这段会话是 v4 之前的旧格式」—— **文案错误**（真实原因是 surface 首节点还没成为系统提示词）。
- `status.canWrite`（`src/http.js:148`）= `turn && step` 非空，同样不含 protectedHead 条件，
  前端据此显示「当前会话已可立即写入，点『同步到会话』即可应用」（`src/client.js:1500`），
  在「turn 开着但系统提示词还没落 surface」的窗口里是**错的**（正是 B1 的触发窗口）。
- 代码注释 `src/http.js:131` 仍写着「v4 会话空闲也能写」，与 `src/history.js:817-824` 相反；
  `README.md:131/296-301/331` 有同样的过期说法。

### B6（轻）文档漂移

- `src/http.js:9-12` 文件头 op 列表缺 `delete-files`、`save-segments`、`set-inject`、
  `edit-pending`、`drop-pending`、`repair-capability`、`repair-sessions`。
- `README.md` 的 HTTP 表（约 487-509 行）同样缺 `delete-files`、`save-segments`、`set-inject`、
  `repair-capability`、`repair-sessions`，也没写 `status` 的 `queue/canWrite/version` 字段。

### B7（轻）`written` / `skipped` 类型歧义

| op | `written` | `skipped` |
| --- | --- | --- |
| `import-entries` | **数组**（写成功后的条目 id）`src/http.js:856/875/884` | **数组** `[{name,index,reason}]` `src/http.js:861/884` |
| `import-session` | 无此字段（用 `imported` 数字 + `seqs`） | **数字**（条数）`src/http.js:808` |

前端按「import-entries 的 written / skipped 都是数组；import-session 的 imported / skipped 是数字」
分别写死（`src/client.js:846-853` 对 `900-905`），并且对 `written` 额外做了「数字也认」的兼容分支
（`src/client.js:846-849`）。同名不同型，建议统一为 `written: {ids[], count}` /
`skipped: {count, reasons[]}`。

## 8. 变更接口时的检查清单

1. 新增 / 改动的 op 是否可能写会话日志？是 → 必须经过 `writablePosition`，并**同时**确认
   「surface 首节点已是 system/message」（B1）。
2. 失败原因是否回给用户（`ok:false,error` 或 `skippedReasons` / `warnings`）？不要静默吞。
3. 空闲时是否可能抛 `session-write-pending`？是 → 必须能被 `handlePost` 入队，
   返回形状要能让前端区分「完成」与「已排队」（`queued:true`）。
4. 重复调用是否安全？不安全就把 `message.id` / 队列项 id 这类幂等键带上（B3、B4）。
5. 前端依赖字段有没有变（第 6 节）？改名前先改 `src/client.js`。
6. 跑 `node --test tests/*.test.mjs`（115 项），并手工验证空闲 / request 两个时机（第 2 节）。
